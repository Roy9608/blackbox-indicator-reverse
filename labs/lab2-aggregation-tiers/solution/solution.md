# Lab 2 解答 —— 左闭右开 [a, b)

> 先做 `worksheet.md`。这里是答案 + 完整推理链。
> 黑盒口径（`params.lock`）：档位边界 [1000, 3000, 10000]，
> 分类式 `bisect_right(EDGES, quote)`，即 **[a, b) 左闭右开**。

## 一句话结论

**App 的档位是左闭右开区间：[0,1000) / [1000,3000) / [3000,10000) / [10000,∞)。**
恰好等于 1000、3000、10000 的成交，归**下一段**，不归你直觉里的那段。

## 证据其实从第 0 步就上了桌面

回看 demo 卡片（1h 2026-09-19 12:00）：

```
  巨单          -10,000.00       1
```

一笔**恰好** 10,000.00 的成交被计入了**巨单**（≥10k），而不是大单。
如果 App 用 "(a, b]"（含上界），这笔应落在大单。单条证据即定案——
但初见时几乎没人会停下来想"怎么会有这么整的成交"。

**三个签名，一眼定位边界问题：**

1. 残差全部是 **±1000 / ±3000 / ±10000 的整数组合**——恰好是档位边界的值。
   正常的加总错误不会长这样。
2. **相邻档符号相反、相互抵消**——同一笔成交被放进了邻档。
3. **每行加总恒为 0** → 总净流入完全正确，错的只是**结构**。

第 3 点是这类错误最阴险的地方：如果你的验收标准只有"总量对不对"，
这题永远不会被发现。**对账必须逐档逐点（铁律 2），不能只看合计。**

## 正确分类的实现

```python
from bisect import bisect_right

EDGES = [1000.0, 3000.0, 10000.0]

def tier_of(quote):
    # [0,1000) / [1000,3000) / [3000,10000) / [10000,∞)
    return bisect_right(EDGES, quote)
    # quote=1000  -> 1（中单）   左闭：含下界
    # quote=3000  -> 2（大单）   右开：不含上界
```

**亲手验证**（worksheet 任务 3）：

```python
bisect_left([1000, 3000, 10000], 1000)   # -> 0  小单（(a,b] 世界）
bisect_right([1000, 3000, 10000], 1000)  # -> 1  中单（[a,b) 世界）✓ App 用这个
```

## 和铁律 4 的关系：同一个纪律，两处应用

铁律 4（`docs/03-iron-laws.md`）说的是**时间切片**：

```python
# ❌ j 用 bisect_right 会把 hi 时刻的数据多算一格，整列错位
i = bisect.bisect_right(buckets, lo)
j = bisect.bisect_right(buckets, hi)
# ✅ 时间切片两端都用 bisect_left
i = bisect.bisect_left(ts_list, t0)
j = bisect.bisect_left(ts_list, t1)
```

本题说的是**数值分档**：`bisect_right(EDGES, q)` 恰好给出 [a, b)。

两者共享同一条纪律：**Python 的 bisect 家族 + 半开区间约定，
 left 是切片的默认，right 是分档的默认——混用即错位。**
症状也不同：切片错位 = "第 N 桶 == 原始第 N−1 桶"（整列平移）；
分档错位 = "残差全是边界值、相邻档反号抵消"。

## 数据说明（诚实披露）

数据集 `labs/data/trades.csv` 中故意埋了 45 笔恰好等于
1000 / 3000 / 10000 的成交（生成器 `generate_trades.py` 公开可查）。

真实对账中它们的残差占比更小、更容易被"看起来差不多"掩盖。
